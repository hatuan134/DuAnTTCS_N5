# S2-03.2 — Chuyển bản sao sang Đang sửa chữa an toàn và có lịch sử

## Phạm vi và quy tắc áp dụng

Triển khai trực tiếp trên source DuAnTTCS_N5(20261002-043841).zip. Người dùng đã đồng ý bổ sung dữ liệu phiếu mượn tối thiểu do source chưa có dữ liệu mượn/trả.

- Chỉ chuyển AVAILABLE (Sẵn sàng) sang REPAIR (Đang sửa chữa).
- Lý do bắt buộc, bỏ khoảng trắng đầu/cuối, tối đa 2.000 ký tự. Không thêm số ký tự tối thiểu tùy ý ngoài yêu cầu không trống.
- LIBRARIAN, LIBRARY_MANAGER và ADMIN được thao tác/xem lịch sử, theo quyền quản lý bản sao hiện có. READER không được gọi API này.
- Kiểm tra loan_items.returned_at IS NULL, đồng thời chặn trạng thái BORROWED cũ dù chưa có phiếu mượn tương ứng.
- Khóa ghi trên bản sao; đổi trạng thái và ghi lịch sử trong cùng transaction. Nếu ghi lịch sử thất bại, transaction phải rollback.
- Lịch sử gồm trạng thái trước/sau, ID và tên người thực hiện lấy từ tài khoản đăng nhập, thời điểm máy chủ, lý do. Tên được lưu tại thời điểm thao tác. Không có API sửa/xóa; PostgreSQL chặn UPDATE, DELETE, TRUNCATE bảng lịch sử.
- Giữ nguyên copyCount là tổng bản sao; thêm availableCount. Tra cứu công khai vẫn giữ đầu sách có bản sao, kể cả khi còn 0 bản Sẵn sàng.
- API trả số khả dụng mới sau khi giao dịch commit. Tab công khai cùng trình duyệt nhận thông báo BroadcastChannel; các trình duyệt/máy khác tự tải lại mỗi 3 giây khi tab đang hiển thị và khi quay lại tab. Đây không phải cơ chế đẩy thời gian thực giữa mọi máy; cập nhật giao diện khác máy có độ trễ theo chu kỳ và mạng.
- Nền tảng mới: loans (phiếu mượn), loan_items (bản sao và thời điểm trả). Trigger khóa cùng dòng bản sao, chỉ nhận bản AVAILABLE, tự đặt BORROWED; khi ghi returned_at thì trả về AVAILABLE. Mỗi bản sao chỉ có một lượt mượn chưa trả. Không có giao diện/API mượn, trả, gia hạn, phạt, đặt trước trong lát này. Nhóm làm các backlog sau phải tái sử dụng các bảng và quy tắc này.
- Không thêm chức năng REPAIR → AVAILABLE, thanh lý hoặc đổi trạng thái tùy ý. Các thao tác dữ liệu mượn/trả phục vụ kiểm thử không phải một module mượn/trả đã hoàn thiện.

Để kiểm tra API bằng DevTools: tab Network → thực hiện một request → Copy as fetch. Dán vào Console và thay URL/body theo bảng; giữ token của chính tài khoản đang kiểm thử, không chia sẻ token. Thực hiện thao tác GET/POST đúng đường dẫn bên dưới. Với Bạn đọc, dùng token của tài khoản Bạn đọc để kiểm tra backend thay vì chỉ quan sát nút bị ẩn.

API:

```text
POST /api/v1/book-copies/{id}/repair
Authorization: Bearer <token của tài khoản đang kiểm thử>
Content-Type: application/json
{"reason":"Bong gáy sách"}

GET /api/v1/book-copies/{id}/status-history
GET /api/v1/books/public
```

Bài kiểm tra PostgreSQL (tạo dữ liệu tạm rồi ROLLBACK, không thay dữ liệu demo):

```powershell
docker cp ".\backend\src\test\resources\S2-03.2-database-regression.sql" duanttcs_n5_postgres:/tmp/S2032-regression.sql
docker compose exec -T postgres sh -c 'psql -v ON_ERROR_STOP=1 -U $POSTGRES_USER -d $POSTGRES_DB -f /tmp/S2032-regression.sql'
```

Kỳ vọng NOTICE PASS và ROLLBACK, không có ERROR. Bài SQL kiểm tra nền tảng mượn/trả, rollback cặp cập nhật trạng thái/lịch sử, chặn sửa/xóa lịch sử và chặn ghi lượt mượn trên bản REPAIR. Bài này không thay thế kiểm thử HTTP với transaction Spring.

Chạy unit test/build tại máy bạn:

```powershell
cd backend
.\mvnw.cmd "-Dtest=BookCopyRepairServiceTest,BookCopyPermissionTest,BookCopyUpdateControllerTest,BookCopyUpdateServiceTest,BookCopySummaryServiceTest,BookCatalogServiceTest" test
cd ..\frontend
npm.cmd run build

```

Kiểm thử cạnh tranh với thao tác mượn: trên database test, trong một phiên SQL BEGIN rồi thêm loan_items cho bản AVAILABLE, chưa COMMIT. Gửi request repair cùng bản từ UI; request phải chờ khóa. COMMIT phiên mượn; repair phải bị từ chối. Đảo thứ tự (repair commit trước, thêm loan_items sau) thì database phải từ chối ghi lượt mượn trên REPAIR. Không để phiên SQL mở lâu sau kiểm thử.

1. Đăng nhập Thủ thư, mở đầu sách demo và tab công khai: 2 Sẵn sàng / 3 bản sao.
