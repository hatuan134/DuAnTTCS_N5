# S2-05.5 — Đảm bảo thời gian tra cứu với 5.000 đầu sách

Bản triển khai dựa trên ZIP `DuAnTTCS_N5(4).zip`, giữ API và trang `/catalog` của S2-05.1–S2-05.4.

**Trạng thái:** đã có mã tối ưu, bộ dữ liệu và công cụ nghiệm thu. **Chưa xác nhận đạt AC5**: chưa có phép đo trên PostgreSQL thật và chưa có xác nhận mốc đo/kịch bản từ PO. Không sử dụng các con số giả định làm kết quả nghiệm thu.

## 1. Phạm vi và kiến trúc

- Backend thực tế: Java 17, Spring Boot 4.1.1; package `com.duanttcsn5.library`; JPA, Flyway, PostgreSQL 15. Frontend React 18/TypeScript/Vite/Tailwind.
- Mở rộng `BookRepository`, `BookCopyRepository`, `BookCatalogService`. Không tạo một controller/service quản lý sách khác.
- Thay việc tải toàn bộ sách, chuẩn hóa, lọc, dựng DTO và sort trong Java bằng SQL count + sort + LIMIT/OFFSET. Chỉ fetch entity và thống kê bản sao của tối đa 20 ID ở trang được chọn.
- Count và truy vấn trang dùng cùng điều kiện. Giao dịch REPEATABLE_READ giúp tổng, trang và số bản sao cùng nhìn một snapshot dữ liệu.
- Trường tìm kiếm là generated column STORED: PostgreSQL tự cập nhật khi sửa nhan đề, ISBN hoặc tên tác giả; không có cache kết quả làm cũ trạng thái mượn.
- Điểm phù hợp được giữ: nhan đề chính xác/khớp một phần 100/40, tác giả 80/30, ISBN 120/20. Điểm tác giả chỉ lấy lớn nhất, không cộng nhiều lần. Tie: nhan đề không dấu tăng dần, rồi ID. Năm xuất bản giảm dần, NULL ở cuối.
- Có bản sao mới được xuất hiện công khai. Bản rảnh = AVAILABLE và không có `loan_items.returned_at IS NULL`; vẫn tìm tác giả chính cũ và đồng tác giả, giữ thể loại ngừng sử dụng có sách công khai.
- Bộ lọc lấy projection DISTINCT thể loại/năm, không hydrate 5.000 entity để dựng dropdown.
- Không sửa entity, DTO, controller, router, JWT, quyền, quy tắc tạo sách hay API response. `SecurityConfig` hiện đã cho phép `/api/v1/books/public/**`. API quản trị vẫn kiểm tra ADMIN/LIBRARY_MANAGER/LIBRARIAN như cũ.
- API `/books/public` cũ được giữ tương thích; đường tra cứu phân trang đang dùng trên website là `/books/public/search` và được tối ưu trong lát này.
- Không làm thêm mượn/trả, tìm nâng cao mới, cache trạng thái, Elasticsearch, sửa migration cũ hay nạp tự động 5.000 sách vào database chạy thật.
- Bộ đo nằm riêng trong `scripts/performance`; Playwright là dependency công cụ kiểm thử, không thêm vào frontend hoặc backend.

Nguồn đối chiếu PostgreSQL: [normalize/NFD](https://www.postgresql.org/docs/15/functions-string.html) và [stored generated columns](https://www.postgresql.org/docs/15/ddl-generated-columns.html). Database cần UTF8 như image postgres:15 hiện tại. Không cần extension unaccent/pg_trgm.

## 5. Chạy ứng dụng và nạp dữ liệu

Ưu tiên cách chạy đã có:

```powershell
.\RUN_ALL.cmd
```

Nếu backend đang chạy từ phần trước, dừng backend và khởi động lại để mã mới và Flyway V16 được áp dụng. Kiểm tra log có `Started LibraryManagementBackendApplication`, không chỉ có BUILD SUCCESS.

Mở http://localhost:5173/catalog; không cần đăng nhập để tra cứu.

Nạp bộ dữ liệu mẫu trong một terminal khác tại gốc dự án. Dùng database local kiểm thử; script thêm dữ liệu, không xóa dữ liệu hiện tại và không tự chạy khi khởi động ứng dụng.

```powershell
cd C:\Dev\DuAnTTCS_N5
& .\scripts\Import-Env.ps1
$OutputEncoding = [System.Text.UTF8Encoding]::new($false)
Get-Content .\backend\src\test\resources\S2-05.5-demo-data.sql -Raw -Encoding UTF8 | docker compose exec -T -e PGCLIENTENCODING=UTF8 postgres psql -v ON_ERROR_STOP=1 -U $env:DB_USERNAME -d $env:DB_NAME
```

Kết quả: `fixture_books = 5000`; các trạng thái cộng lại đủ 15.000 bản sao (3.334 AVAILABLE, 1.666 HELD, 5.000 REPAIR, 5.000 REMOVED). Script dùng sequence có sẵn, không hard-code ID. Chạy lại không thêm trùng. Nếu trùng ISBN với sách khác hoặc dữ liệu mẫu bị sửa, script/nghiệm thu sẽ báo lỗi; không âm thầm ghi đè dữ liệu.

Mẫu này không tạo phiếu mượn mới. Trường hợp bản sao AVAILABLE nhưng đang có khoản mượn chưa trả được kiểm tra riêng bằng test PostgreSQL TEMP table.

## 7. Chạy phép đo API và giao diện thật

Ứng dụng và PostgreSQL phải đang chạy; đã nạp dữ liệu mẫu. Node/npm đã có vì frontend dùng Vite. Công cụ cài riêng, không thay package của frontend:

```powershell

$env:S2055_LABEL = 'after'
```

Công cụ mở Chromium headless, kiểm tra toàn bộ 250 trang để xác nhận 5.000 sách, đối chiếu nhan đề/tác giả/thể loại/năm/bản sao với công thức dữ liệu mẫu, rồi chạy 8 kịch bản. UI được thao tác trên chính `/catalog` hiện có. Nó so sánh ID, thứ tự, metadata, toàn bộ tác giả và số bản rảnh cho TỪNG mẫu. Tải dữ liệu chuẩn bị không nằm trong mẫu thời gian và làm ấm cache, được ghi rõ trong báo cáo.

Kết quả được lưu trong `docs/sprint/S2-05.5-results/<label>-<timestamp>/`:

- `results.json`: cấu hình môi trường, truy vấn, từng mẫu, lỗi nếu có, max/p95 theo kịch bản/API/UI.
- `results.csv`: mỗi dòng một lần đo, số ms chưa làm tròn để xét đạt, đúng/sai và PASS/FAIL.
- Exit code 0 chỉ khi tất cả 160 mẫu đạt. Sai dữ liệu/chậm/API lỗi/UI lỗi trả exit code 1. Thiếu dữ liệu hoặc server không chạy: `SETUP_FAILED`, không có kết quả đạt giả.
- Dòng `maxMs < 1500` phải đi cùng `failures = 0`, đủ số samples và dữ liệu đúng. Không chỉ nhìn p95.

Xem trình duyệt thao tác khi demo:

```powershell

npm run benchmark
```

Đổi port nếu cấu hình local khác mặc định:

```powershell
$env:S2055_API_URL = 'http://localhost:8080/api/v1'
```

Nếu dùng Vite preview khi đo, đặt đúng URL/port đã chạy. Ghi rõ dev hay bản production build trong biên bản và dùng cùng cấu hình khi so sánh trước/sau.

Đo trước tối ưu: khi vẫn ở mã S2-05.4, copy RIÊNG file seed và thư mục công cụ, nạp seed trên schema V15 rồi chạy với `S2055_LABEL='before'`. Nếu đã áp patch thì không bịa kết quả before; báo cáo after vẫn có giá trị nghiệm thu tuyệt đối.

Sau MỖI lần điều chỉnh: đặt label khác, chạy lại toàn bộ 8 kịch bản với 10 lần. Nếu API chậm, xem truy vấn/count/join bằng EXPLAIN ANALYZE trong môi trường test; nếu API nhanh nhưng UI chậm, kiểm tra render/browser/mạng. Chỉ kết luận tối ưu có hiệu quả sau lần đo lại, không dựa vào dự đoán.
